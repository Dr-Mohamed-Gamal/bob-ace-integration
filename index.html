IBM Bob on App Connect Enterprise

Six prompts that take, with nothing asked of the developer, an integration requirement to a built, documented, reviewed and changed REST service on IBM App Connect Enterprise (ACE) and IBM API Connect, with IBM Bob Shell running inside the ACE Toolkit.

Pilot use cases for a bank's integration team · dry runs and a clean rehearsal on 5 October 2026 · ACE 13.0.9, Bob Shell 2.0.5

The bank's documents, code and the reports made from them are not published here. The runs used mock requirement documents prepared for the pilot. This page describes the inputs and why each is used, the method, every prompt as sent, and what the runs showed.

The use cases

The bank's integration team builds and changes REST services in two layers: an API on API Connect that channels call, and an ACE service behind it that maps JSON to the back end's XML and calls the back end. The team listed six use cases for IBM Bob. Four form the pilot and run here in the order the team agreed:

Use case 1

Create a service

Build a new REST service from a signed-off requirement document: the API Connect API and product, and the ACE REST API project behind it.

Use case 3

Document it

Write the service's Interface Definition Document in the bank's template, from the code as built.

Use case 6

Review it

Review the service against the requirement and the bank's standards, report findings by rule, file and line, then fix the accepted ones.

Use case 2

Change it

Apply a change requirement to the existing service: new fields, conditions and defaults, with change comments and an updated document.

Use cases 4 (troubleshooting) and 5 (root-cause analysis) were parked for a later phase.

The input data, and why each is used

The bank cannot circulate its requirement documents, so IBM prepared mock ones in the bank's own layouts, for an invented loyalty-points project with an invented back end called LMS. The layouts matter more than the content: they are what Bob has to read and fill in on real work.

How it works

  • Bob Shell in the ACE Toolkit. The Toolkit's Local Terminal gets an "IBM Bob Shell" entry that starts Bob in the Toolkit workspace, so Bob writes the same files the Toolkit opens. All prompts run in one chat, in Bob's built-in Agent mode.
  • Two rules files in .bob/rules/, read on every turn: the bank's standards, and IBM's working method for Bob, kept apart so the bank can see which is which. No custom mode is used.
  • IBM's ACE skills. The Toolkit adds IBM's open-source ace-flowpilot skills to the workspace when it opens it. They teach Bob the exact project files, node types and ESQL patterns ACE expects. Without them, the first dry run produced ACE files the Toolkit could not open.
  • A Toolkit check Bob runs himself. tools/toolkit_check.py runs the Toolkit's own build and validators headless (mqsicreatebar -cleanBuild on a copy of the project) and prints the Toolkit's problem markers. It reproduces the Toolkit's Problems view exactly, so Bob can see what the Toolkit would show, and it fails when the BAR holds no compiled flow, so a project the Toolkit does not recognise cannot pass.
  • A runtime check Bob runs himself. tools/runtime_check.py deploys the REST API to a local, throw-away integration server and calls it with the requirement's cases against a mock back end: validation errors, success mapping, back-end error, timeout, and the change's conditions and defaults. A project that builds is not yet a service that works; this check shows the difference, and Bob corrects what it reports. Since 8 October it also takes a cases file Bob writes from the requirement (--cases, rule IBM-26), so the cases are not hard-coded for one service, and in that mode the run fails if the integration server log shows an error.
  • A decisions file. Bob records every decision the lead gives him in docs/decisions.md. Later steps and reviewers read it.
  • Reviews in a fresh context. The review prompt asks Bob to use a subagent: a second Bob with its own context that never saw the build, reads every file as it is, and reruns the checks.

What the runs showed

Three runs on 5 October: an afternoon dry run, a night run that tested every use case, and a clean rehearsal from a reset workspace with the final prompts. Every step was checked three ways: the Toolkit check, an audit script (invented values, requirement fields, status codes, schema names), and a person reading the diff.

What the runs taught

  • Reviews in the same context approve their own work. Twice a same-context review reported zero findings on code with real defects. The same prompt with a subagent found eight real ones, including a typo in a JSON key that the audit had missed too.
  • A model guesses values it does not have. The first build put three invented hosts on the bank's real domain into the API and the ESQL, and copied the example requirement id from the rules into a change comment. Rule IBM-01 (placeholders only) stopped it in every later run.
  • The Toolkit is the judge, and Bob cannot see it. Bob's first ACE project compiled with ibmint but would not open in the Toolkit. Bob cannot read the Problems view; the headless Toolkit check gives him its errors. It does not report warnings, so a person still looks at the Problems view after each step.
  • A project that builds is not yet a service that works. Deploying earlier outputs on a local integration server showed what neither the build nor a review had shown: a compute mode value, the response parser domain, where errors are caught. The runtime check now runs these cases at every step.
  • A rule can cause a defect. A rule told Bob to move reusable procedures to schema level without saying such a procedure cannot touch the message trees. Bob followed it and created seven Toolkit warnings. Rules need the same review as code.

Six prompts, no questions, 8 October

The team asked that the developer supplies no answers and that Bob tests the flows itself with data from the requirement. Prompt 2's decisions block became rule IBM-24, rule IBM-25 tells Bob to decide and record instead of asking, and prompt 1 now plans and builds in one go; prompts 2 to 6 are unchanged. Rule IBM-26 and the runtime check's cases-file mode cover the testing. One headless run of the six prompts in one chat: no questions, nine decisions recorded, every check green at every step (7 of 7 cases after the build, 13 of 13 after the change), three real findings in the first review and none in the change review. 23.4 Bobcoins. The only error was Bob's service dropping the first review request; the same prompt sent again completed. Rule IBM-26 was then tried in a fresh chat: Bob wrote 15 cases from the two requirement documents and passed 15 of 15 with a clean server log on its first run, 0.9 Bobcoins.

The two rules files, and what changed

During the runs, each mistake Bob made became a rule. On 5 October those rules went into the bank's standards file, which mixed the bank's standards with IBM's instructions to Bob. On 6 October they were split into two files, so the bank's file holds only its standards and IBM's method is labelled as IBM's. Bob reads both, so it works the same way.

Made ready for the bank's real workspace

The runs used mock documents in an empty workspace. Before Bob works on the bank's real code, four rules were adjusted on 6 October so they cannot steer it wrong there:

  • IBM-01 lets Bob reuse names already in the workspace, as the bank's FW-04 requires; only values found nowhere become placeholders.
  • IBM-04: the Toolkit check runs on Windows, macOS and Linux, and when it cannot find ACE Bob asks the developer for the Problems view instead.
  • API-08 adds the full set of status codes to new APIs only; a change updates only the responses its requirement covers.
  • FW-10 is marked "to be confirmed" with the bank's middleware team, and a change keeps a service's existing project type.

Running it

  1. Install ACE 13 with its Toolkit, IBM Bob Shell and Python 3. Get from the pilot lead the four files this repository does not publish: the two requirement documents and the Interface Definition Document template (Markdown and Word).
  2. Clone the repository and run python3 tools/new_workspace.py: it creates bob-workspace/ with the rules, the .bobignore file and the folders, and lists the files still to add. If the repository has a documents/ folder the script copies the documents in; otherwise put them in requirements/ and templates/. The workspace is git-ignored.
  3. Open the ACE Toolkit on bob-workspace; it installs IBM's ace-flowpilot skill itself. Settings > Terminal > Local Terminal > add an "IBM Bob Shell" entry that runs tools/bob-shell-toolkit.sh with the workspace as the working directory.
  4. Window > Show View > Terminal, open an "IBM Bob Shell" terminal, and send the six prompts in one chat, each pasted as one line with the author and date filled in. Prompt 4 is written from the review's findings.
  5. Approve the checks when Bob asks. After each step, run python3 ../tools/toolkit_import.py on the project once, or File > Import, and read the Problems view.
  6. Expect, from the 8 October run: no question, both checks green after prompts 1 and 5, three findings in the first review and none in the second, about 25 Bobcoins. The cases file (IBM-26) was tested in its own chat; its place inside prompts 1 and 5 has not yet run as one flow, so the first full run is also that test.
