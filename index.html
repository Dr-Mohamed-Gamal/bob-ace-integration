IBM Bob on App Connect Enterprise

Seven prompts that take an integration requirement to a built, documented, reviewed and changed REST service on IBM App Connect Enterprise (ACE) and IBM API Connect, with IBM Bob Shell running inside the ACE Toolkit.

Pilot use cases for a bank's integration team · dry runs and a clean rehearsal on 5 October 2026 · ACE 13.0.9, Bob Shell 2.0.5

The bank's documents, code and the reports made from them are not published here. The runs used mock requirement documents prepared for the pilot. This page describes the inputs and why each is used, the method, every prompt as sent, and what the runs showed.

The use cases

The bank's integration team builds and changes REST services in two layers: an API on API Connect that channels call, and an ACE service behind it that maps JSON to the back end's XML and calls the back end. The team listed six use cases for IBM Bob. Four form the pilot and run here in the order the team agreed:

Use case 1

Create a service

Build a new REST service from a signed-off requirement document: the API Connect API and product, and the ACE REST API project behind it.

Use case 3

Document it

Write the service's Interface Definition Document in the bank's template, from the code as built.

Use case 6

Review it

Review the service against the requirement and the bank's standards, report findings by rule, file and line, then fix the accepted ones.

Use case 2

Change it

Apply a change requirement to the existing service: new fields, conditions and defaults, with change comments and an updated document.

Use cases 4 (troubleshooting) and 5 (root-cause analysis) were parked for a later phase.

The input data, and why each is used

The bank cannot circulate its requirement documents, so IBM prepared mock ones in the bank's own layouts, for an invented loyalty-points project with an invented back end called LMS. The layouts matter more than the content: they are what Bob has to read and fill in on real work.

How it works

  • Bob Shell in the ACE Toolkit. The Toolkit's Local Terminal gets an "IBM Bob Shell" entry that starts Bob in the Toolkit workspace, so Bob writes the same files the Toolkit opens. All prompts run in one chat, in Bob's built-in Agent mode.
  • The rules file in .bob/rules/ holds the standards. No custom mode is used.
  • IBM's ACE skills. The Toolkit adds IBM's open-source ace-flowpilot skills to the workspace when it opens it. They teach Bob the exact project files, node types and ESQL patterns ACE expects. Without them, the first dry run produced ACE files the Toolkit could not open.
  • A Toolkit check Bob runs himself. tools/toolkit_check.py runs the Toolkit's own build and validators headless (mqsicreatebar -cleanBuild on a copy of the project) and prints the Toolkit's problem markers. It reproduces the Toolkit's Problems view exactly, so Bob can see what the Toolkit would show.
  • A decisions file. Bob records every decision the lead gives him in docs/decisions.md. Later steps and reviewers read it.
  • Reviews in a fresh context. The review prompt asks Bob to use a subagent: a second Bob with its own context that never saw the build, reads every file as it is, and reruns the checks.

The seven prompts

As sent in the clean rehearsal. <date> is today's date.

1Plan the serviceUse case 1 · 0.65 Bobcoins
Read `requirements/API-SRS-Project_MOCK_Loyalty_Rewards-V1.0.md`. Tell me how you will build LoyaltyPointsInquiryAPI: which layer each part goes in, the files you will create, and any question you have. Do not create anything yet.
Nothing is written before a person has seen the plan. Bob decides the layers from the requirement's scope table, lists every file, lists the placeholders it will need, and asks what the requirement leaves open. In two runs it asked five and six questions, and the questions differed.
2Answer and buildUse case 1 · 5.61 Bobcoins
Answers and decisions: no broker schema (files in the project root, like ExampleAPI). There is no framework in this workspace: keep it self-contained, write no new libraries, and mark each plug-in point with `TODO framework`. The user-defined property for the LMS URL is `LMS_URL`. API Connect: base path `/loyalty/v1`, files in `apic/`, calling ACE through the catalog property `omw-loyalty-url`; one product `LoyaltyRewards` (the redemption API joins it later); pipeline values as `TODO_` placeholders. Send no extra headers or credentials to LMS: the SRS names none. Generate X-TRACKING-ID as a UUID in OMW and return it as a response header. Reject an invalid `programCode` with EAI-LMS-BRK-002 and HTTP 400. Build only `LoyaltyPointsInquiryAPI` now and do not write the Interface Definition Document yet. Go ahead and build it as planned.
One block of decisions answers every question Bob asked in either run, so the prompt does not need rewriting for each run. Bob builds the API Connect API, product and pipeline properties, and an ACE REST API project (OpenAPI document, generated main flow, one subflow per operation, ESQL), then runs the Toolkit check, fixes what it reports and runs it again.
3Write the Interface Definition DocumentUse case 3 · 0.87 Bobcoins
Write the Interface Definition Document for the service you just built. Follow `templates/EAI_Interface_Definition_Document_TEMPLATE.md`. Today is <date>.
The document describes the code, not the requirement: processing logic, every input and output field, every error code with its HTTP status, and a diagram of where the service sits. The date matters: without it Bob copied the requirement's date into the document.
4Review in a fresh contextUse case 6 · 1.77 Bobcoins
Review what you built against the standards, using a subagent with a fresh context. Do not change any file.
The reviewer re-reads every file, maps every requirement row to a code line, traces every literal value to the requirement, the prompt or the rules, compares status and error codes, and reruns the Toolkit check. Each finding is one table row: rule id, file and line, what is wrong, the fix. In the rehearsal it found two runtime bugs that the Toolkit check and the audits had passed.
5Fix the accepted findingsUse case 6 · 6.72 Bobcoins
Fix findings F-01, F-04, F-05, F-06, F-07, F-09 and F-12. F-02 and F-03 are by design: there is no framework in this workspace, keep the `TODO framework` markers. F-08 and F-10 stay as placeholders. Keep HTTP 400 for EAI-LMS-BRK-004 (F-11): an LMS error is a functional failure (SRS 2.3). Record these decisions and the ones I gave you before in `docs/decisions.md`. Then run the Toolkit check, and update the Interface Definition Document where the behaviour it describes has changed.
This is the human step of use case 6: a person reads the review and decides which findings to accept. The finding numbers change from run to run; the shape of the prompt does not. Recording the decisions stops the next review from reporting them again.
6Apply the changeUse case 2 · 6.73 Bobcoins
Read `requirements/API_SRS-MOCK_Loyalty_Partner_Redemption_Changes_V1.0.md` and apply the change for LoyaltyPointsInquiryAPI. The requirement id is URF-90001, the author is Mohamed Gamal and the date is <date>.
Bob maps the three new fields with their conditions, adds a change comment with the id, author and date at each change, updates both API definitions and the document's version history, and does not touch or invent the second API, which is not in the workspace.
7Review the changeUse case 6 · 1.43 Bobcoins
Review the URF-90001 change against the change SRS and the standards, using a subagent with a fresh context. Do not change any file.
A second fresh review, on the change only. In the rehearsal it found four real gaps and no false alarms, because it read the decisions file first.

What the runs showed

Three runs on 5 October: an afternoon dry run, a night run that tested every use case, and a clean rehearsal from a reset workspace with the final prompts. Every step was checked three ways: the Toolkit check, an audit script (invented values, requirement fields, status codes, schema names), and a person reading the diff.

Rehearsal stepToolkit checkWhat the checks found
1–2 Plan and buildPass, first timeEvery requirement field mapped, all nine status codes in both API files, no invented values: 21 placeholders, all TODO_… or on the reserved .invalid domain
3 Documentn/aEvery template section and field; the date from the prompt; the error behaviour it describes matches the code
4 Reviewn/a12 findings, 7 real, including an undeclared user-defined property and a validation error that still called the back end. 2 false alarms (no framework, a decision the reviewer could not see), which led to the decisions file
5 FixPassBoth runtime bugs fixed; decisions recorded
6 ChangePassProgramme-code condition, default 'N', guarded output field, dated change comments, both API files, document version raised
7 Review the changen/a4 findings, all real, no false alarms: document file name not renamed to the new version; API version not raised in either API file; a success example without the new field

Rehearsal cost: 23.8 Bobcoins for the seven prompts. Costs rise along the chat because each turn carries the whole conversation.

Three things the earlier runs taught

  • Reviews in the same context approve their own work. Twice a same-context review reported zero findings on code with real defects. The same prompt with a subagent found eight real ones, including a typo in a JSON key that the audit had missed too.
  • A model guesses values it does not have. The first build put three invented hosts on the bank's real domain into the API and the ESQL, and copied the example requirement id from the rules into a change comment. Rule FW-11 (placeholders only) stopped it in every later run.
  • The Toolkit is the judge, and Bob cannot see it. Bob's first ACE project compiled with ibmint but would not open in the Toolkit. Bob cannot read the Problems view; the headless Toolkit check gives him the same messages.

Running it

  1. Install IBM Bob Shell and ACE 13. Open the ACE Toolkit on the Bob workspace.
  2. In the Toolkit: Settings > Terminal > Local Terminal > Add an entry "IBM Bob Shell" that runs tools/bob-shell-toolkit.sh, with the Eclipse workspace as the initial working directory.
  3. Window > Show View > Terminal, open an "IBM Bob Shell" terminal, and send the seven prompts in one chat.
  4. Approve read-only checks for the task when Bob asks; approve deletions once, after reading them.
  5. After each step, refresh the project in the Toolkit and look at the Problems view.

Each use case also has its own page in this repository: use case 1, use case 3, use case 6, use case 2.
